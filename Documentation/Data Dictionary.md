# Data Dictionary
**Project:** Olist E-Commerce Analysis — Power BI
Documents the data model structure: source tables, calculated columns, calculated tables, and Power Query transformations.

---

## Source Tables (Olist dataset)

| Table | Grain | Role |
|---|---|---|
| `orders` | One row per order | Fact table — order lifecycle dates, status |
| `order_items` | One row per line item | Fact table — price, freight per product per order |
| `customers` | One row per order-customer record | Dimension — links `customer_id` (per-order) to `customer_unique_id` (per-person) |
| `order_payments` | One or more rows per order | Fact table — payment method/value, supports split payments |
| `order_reviews` | One row per review | Fact table — review score and text per order |
| `products` | One row per product | Dimension — includes merged English category name |
| `sellers` | One row per seller | Dimension |
| `Category Translation` | One row per category | Lookup — Portuguese → English category names, merged into `products` |
| `Date Table` / `Dim_Date` | One row per calendar day | Custom calendar table, marked as Date Table |

**Key relationships (star schema, single direction, `orders` as hub):**
- `Date Table[Date]` → `orders[Order Date Only]` (1-to-many)
- `customers[customer_id]` → `orders[customer_id]` (1-to-many)
- `orders[order_id]` → `order_items[order_id]` (1-to-many)
- `orders[order_id]` → `order_payments[order_id]` (1-to-many)
- `orders[order_id]` → `order_reviews[order_id]` (1-to-many)
- `products[product_id]` → `order_items[product_id]` (1-to-many)
- `sellers[seller_id]` → `order_items[seller_id]` (1-to-many)

## Calculated Columns

### `orders` table

**Order Date Only**
```dax
Order Date Only = DATEVALUE(orders[order_purchase_timestamp])
```
Strips the time component from the purchase timestamp, producing a pure Date value. Created specifically to fix a broken relationship to `Date Table[Date]` — the original timestamp column (with time-of-day) failed to match against the date-only calendar table, causing most orders to fall into an unmatched "blank" bucket in date-based visuals.

**Delivery Delay (Days)**
```dax
Delivery Delay (Days) = 
DATEDIFF(orders[order_estimated_delivery_date], orders[order_delivered_customer_date], DAY)
```
Days between the estimated and actual delivery date. Negative or zero = delivered on/before estimate. Positive = delivered late.

**Delivery Status**
```dax
Delivery Status = 
IF(orders[Delivery Delay (Days)] > 0, "Late", "On Time")
```
Binary classification derived from `Delivery Delay (Days)`. Used throughout the Delivery & Satisfaction page and in the `% Orders Late` / `Avg Review Score (Late/On Time)` measures.

**Delay Bucket**
```dax
Delay Bucket = 
SWITCH(
    TRUE(),
    orders[Delivery Delay (Days)] <= 0, "On Time / Early",
    orders[Delivery Delay (Days)] <= 3, "1-3 Days Late",
    orders[Delivery Delay (Days)] <= 7, "4-7 Days Late",
    "8+ Days Late"
)
```
Groups delivery delay into four bands, used to show the *gradient* of how satisfaction degrades with increasing lateness (rather than just a binary late/on-time split).

**Delay Bucket Sort**
```dax
Delay Bucket Sort = 
SWITCH(
    TRUE(),
    orders[Delivery Delay (Days)] <= 0, 1,
    orders[Delivery Delay (Days)] <= 3, 2,
    orders[Delivery Delay (Days)] <= 7, 3,
    4
)
```
Hidden helper column providing a numeric sort key for `Delay Bucket`, since the text labels don't sort correctly alphabetically. Linked via **Sort by column** on `Delay Bucket`.

## Calculated Tables

### `RFM_Table`
```dax
RFM_Table = 
ADDCOLUMNS(
    SUMMARIZE(orders, customers[customer_unique_id]),
    "Frequency", CALCULATE(DISTINCTCOUNT(orders[order_id])),
    "Monetary", CALCULATE([Total Revenue]),
    "RecencyDays", CALCULATE(
        DATEDIFF(
            MAX(orders[order_purchase_timestamp]), 
            CALCULATE(MAX(orders[order_purchase_timestamp]), ALL(orders)), 
            DAY
        )
    )
)
```
A calculated table, grouped to one row per unique customer (`customer_unique_id`), built from the `orders` table. Purpose: raw fact tables are order-grain, but customer segmentation requires customer-grain data — this table performs that grouping.

**Columns produced:**
| Column | Meaning |
|---|---|
| `customer_unique_id` | Grouping key — one row per real-world customer |
| `Frequency` | Count of distinct orders placed by that customer |
| `Monetary` | Total revenue generated by that customer (calls the `Total Revenue` measure, filtered to the customer) |
| `RecencyDays` | Days between this customer's most recent order and the single most recent order date in the *entire dataset* (not `TODAY()` — the dataset is frozen at Oct 2018, so recency is anchored to the dataset's own end date to remain meaningful) |

**Segment** (calculated column added on top of `RFM_Table`)
```dax
Segment = 
SWITCH(
    TRUE(),
    RFM_Table[Frequency] >= 2 && RFM_Table[Monetary] >= 500, "Champions",
    RFM_Table[Frequency] >= 2, "Loyal",
    RFM_Table[RecencyDays] <= 90, "New / Recent",
    RFM_Table[RecencyDays] > 180, "At Risk / Lost",
    "Standard"
)
```
Classifies each customer into one of five behavioral segments. Thresholds (2+ orders, R$500 spend, 90/180-day recency windows) were set as reasonable starting points and validated against the resulting distribution rather than derived statistically.

**Confirmed segment distribution (from live model):**
| Segment | Customers |
|---|---|
| At Risk / Lost | 66,182 |
| Standard | 17,691 |
| New / Recent | 9,226 |
| Loyal | 2,608 |
| Champions | 389 |

## Power Query Transformations

### `products` query
- Merged with `Category Translation` table (Left Outer join on `product_category_name`) → expanded `product_category_name_english` → renamed to `product_category`. All visuals use this English column, never the raw Portuguese field.
- Nulls in `product_category` filled with `"Unknown"`.

### `customers` query
- Added custom column **`State Name`**: maps Brazilian state abbreviations (e.g., `SP`, `RJ`) in `customer_state` to full state names (e.g., "São Paulo", "Rio de Janeiro") via a nested `if/then/else` custom column. Built specifically to make state-level visuals (matrix, filters) readable to a non-Brazilian audience, since two-letter codes aren't self-explanatory.
- Distinction preserved between `customer_id` (generated per-order) and `customer_unique_id` (the true per-person identifier) — all customer-level counting and segmentation uses `customer_unique_id` to avoid treating repeat customers as new ones.

### `orders` query
- Date columns (`order_purchase_timestamp`, `order_approved_at`, `order_delivered_carrier_date`, `order_delivered_customer_date`, `order_estimated_delivery_date`) typed as Date/Time.
- Rows filtered to exclude `order_status` = "unavailable" or "canceled".
- Rows with null `order_delivered_customer_date` where status = "delivered" removed (data quality issue in source).

### `order_items` query
- `price`, `freight_value` typed as Decimal Number.
- Kept at line-item grain — no pre-aggregation, to preserve slicing flexibility by product/category downstream.

### `order_reviews` query
- Removed duplicate reviews per `order_id` (kept most recent by `review_creation_date`).
- `review_score` typed as Whole Number.

### `Date Table` (custom-built via Blank Query, M code)
Manually generated calendar table (`List.Dates`) spanning 2016-01-01 to 2018-12-31, since Olist provides no built-in calendar dimension. Columns: `Date`, `Year`, `MonthNum`, `MonthName`, `Quarter`, `YearMonth`. Marked as a **Date Table** in the model (via `Date` column) to support time-intelligence functions like `DATEADD`.

## Known Data Caveats (for presentation / interview context)

- **Repeat rate is low (3.12%) by nature of the business**, not a data error — Olist is a marketplace with heavy one-time-buyer behavior.
- **RecencyDays is anchored to the dataset's last order date (~Oct 2018), not the current date.** Using `TODAY()` would make every customer appear equally "ancient" since the dataset is historical and frozen.
- **Segment thresholds are business judgment calls**, set as reasonable defaults and validated against the resulting distribution, not statistically derived from the data.
- **`customer_id` vs `customer_unique_id`** is the single most important schema quirk in this dataset — using the wrong one silently breaks repeat-customer and RFM logic (every customer looks like a one-time buyer).
